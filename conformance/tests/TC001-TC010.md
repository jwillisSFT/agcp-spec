# AGCP Conformance Test Cases — Batch 1

**Batch:** TC001–TC010  
**Coverage:** CR-001 through CR-010

## Scope

This document contains the detailed AGCP Conformance Test Cases for Runtime Governance Requirements CR-001 through CR-010.

Each Conformance Test Case:

- Verifies exactly one Runtime Governance Requirement (CR).
- Verifies every Normative Statement (NS) mapped to that CR in the Requirements Traceability Matrix (RTM).
- Defines objective pass/fail criteria and required governance evidence.
- Preserves the one-CR-to-one-TC rule for the AGCP Conformance Test Suite.

---

# TC001 — Submit → Authorized

**Requirement**  
CR-001 — A proposal that satisfies all governance constraints SHALL be eligible for authorization.

**Normative Statements Covered**

- NS-6.5-01
- NS-7.5-01
- NS-8.5-01

**Conformance Level**  
L2 — Ordered Governance Mediation

## Test Objective

Verify that a structurally valid and governance-admissible Proposal progresses through Proposal Qualification, the Governance Decision Function, and Execution Authorization, producing the required positive outcome at each stage.

## Preconditions

- Valid governance policy exists.
- Tenant is active.
- Proposal contains all mandatory governance attributes.
- Action Representation is valid.
- Required Governance Context is present.
- Required evidence is present.
- Canonical State is available and authoritative.
- Applicable authority is valid.

## Request / Scenario

Submit a fully compliant governance Proposal.

## Simulated Execution Trace

Step 1 — Proposal is submitted.

Step 2 — Proposal Qualification executes.

Step 3 — Proposal Qualification produces `Qualified Proposal`.

Step 4 — Governance Decision Function evaluates the Qualified Proposal.

Step 5 — Governance Decision Function produces `Authorized`.

Step 6 — Execution Authorization evaluates the authoritative governance decision.

Step 7 — Execution Authorization produces `Authorized for Commit Boundary Processing`.

## Ledger Delta

```text
ProposalCreated
ProposalQualificationStarted
ProposalQualified
GovernanceDecisionFunctionInvoked
GovernanceDecisionProduced
Decision=Authorized
ExecutionAuthorizationInvoked
AuthorizationOutcome=AuthorizedForCommitBoundaryProcessing
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
AUTHORIZED
```

## Expected Result

```http
200 OK
```

## Pass Criteria

The implementation passes this test only if:

- Proposal Qualification produces exactly one qualification outcome.
- The qualification outcome is `Qualified Proposal`.
- The Governance Decision Function produces an `Authorized` governance outcome.
- Execution Authorization produces `Authorized for Commit Boundary Processing`.
- The Proposal is eligible for Commit Boundary processing.
- Governance Evidence records each stage outcome.

## Fail Criteria

The implementation fails this test if:

- the Proposal bypasses Proposal Qualification;
- governance evaluation occurs before qualification;
- authorization is issued without a Governance Decision Function outcome;
- Execution Authorization is omitted;
- the Proposal becomes executable without the required staged outcomes; or
- Governance Evidence does not record the qualification, decision, and authorization outcomes.

# TC002 — Submit → Pending Human Review

**Requirement**  
CR-002 — Governance evaluation SHALL support escalation and deferred human adjudication paths.

**Normative Statements Covered**

- NS-7.5-01
- NS-13.5-01

**Conformance Level**  
L4 — Execution Authorization Control

## Test Objective

Verify that the Governance Decision Function can produce a deferred human-review outcome and that the governed lifecycle can represent the resulting non-executable pending condition.

## Preconditions

- Governance policy requires human review for the submitted Proposal.
- Proposal is structurally valid.
- Required Governance Context is present.
- Canonical State is available.
- Escalation policy is configured.

## Request / Scenario

Submit a Proposal requiring human governance review before execution may proceed.

## Simulated Execution Trace

Step 1 — Proposal is submitted.

Step 2 — Proposal Qualification succeeds.

Step 3 — Governance Decision Function evaluates the Qualified Proposal.

Step 4 — Escalation condition is detected.

Step 5 — Governance Decision Function produces `Pending Human Review`.

Step 6 — Lifecycle processing records that execution may not proceed until the pending condition is resolved.

## Ledger Delta

```text
ProposalCreated
ProposalQualified
GovernanceDecisionFunctionInvoked
EscalationConditionDetected
GovernanceDecisionProduced
Decision=PendingHumanReview
EscalationCreated
LifecycleStateChanged
State=PendingHumanReview
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
PENDING_HUMAN_REVIEW
```

## Expected Result

```http
202 Accepted
```

## Pass Criteria

The implementation passes this test only if:

- the Governance Decision Function supports `Pending Human Review` as a governance outcome;
- the Proposal does not proceed to Commit Boundary processing while unresolved;
- lifecycle processing preserves the pending condition as non-executable;
- the pending condition can later resolve according to governance policy;
- Governance Evidence records the escalation and pending state.

## Fail Criteria

The implementation fails this test if:

- the Proposal is authorized for commit without required human review;
- escalation is treated as unconditional authorization;
- the pending state permits execution;
- the lifecycle cannot represent the pending condition; or
- no Governance Evidence of escalation is generated.

# TC003 — Mandatory Invariant Failure

**Requirement**  
CR-003 — Actions that violate mandatory invariants SHALL NOT be authorized.

**Normative Statements Covered**

- NS-5.5-01
- NS-7.5-01
- NS-8.5-02

**Conformance Level**  
L2 — Ordered Governance Mediation

## Test Objective

Verify that violation of a mandatory Global Governance Invariant prevents authorization and results in a non-authorizing governance outcome.

## Preconditions

- Mandatory invariant is defined.
- Proposal violates the mandatory invariant.
- Canonical State is available.
- Governance policy and invariant set are active.

## Request / Scenario

Submit a Proposal that violates a mandatory invariant.

## Simulated Execution Trace

Step 1 — Proposal is submitted.

Step 2 — Proposal Qualification executes.

Step 3 — Governance Decision Function evaluates the Proposal against applicable governance policy and invariants.

Step 4 — Mandatory invariant violation is detected.

Step 5 — Governance Decision Function produces `Denied` or `Structural Refusal`, as applicable to the stage where the violation is detected.

Step 6 — Execution Authorization is not granted.

Step 7 — If Execution Authorization is invoked, it produces `Authorization Failure`.

## Ledger Delta

```text
ProposalCreated
ProposalQualificationExecuted
GovernanceDecisionFunctionInvoked
InvariantEvaluationExecuted
InvariantViolationDetected
GovernanceDecisionProduced
Decision=StructuralRefusal
ExecutionAuthorizationNotGranted
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
REFUSED
```

or

```text
DENIED
```

depending on whether the violation is structural or policy-based.

## Expected Result

```http
403 Forbidden
```

## Pass Criteria

The implementation passes this test only if:

- Global Governance Invariants are evaluated or preserved as required;
- the mandatory invariant violation prevents authorization;
- the Governance Decision Function produces a valid non-authorizing outcome;
- Execution Authorization is not granted;
- `Authorization Failure` is produced if authorization processing is attempted;
- Governance Evidence records the invariant failure.

## Fail Criteria

The implementation fails this test if:

- a Proposal violating a mandatory invariant is authorized;
- the invariant violation is ignored;
- execution authorization is issued despite the violation;
- execution becomes possible; or
- evidence does not identify the governance basis for refusal or denial.

# TC004 — Schema Validation Failure

**Requirement**  
CR-004 — Governance evaluation SHALL reject structurally invalid proposals.

**Normative Statements Covered**

- NS-6.3-02
- NS-6.4-02
- NS-6.5-02
- NS-6.7-02

**Conformance Level**  
L1 — Schema & Envelope Validation

## Test Objective

Verify that incomplete, malformed, or structurally invalid Proposals are refused during Proposal Qualification and do not proceed to governance evaluation.

## Preconditions

None.

## Request / Scenario

Submit a malformed Proposal missing required structural elements.

## Simulated Execution Trace

Step 1 — Proposal is received.

Step 2 — Proposal Qualification begins.

Step 3 — Qualification processing checks proposal structure, Action Representation validity, completeness, identity, provenance, Governance Context, and mandatory governance attributes.

Step 4 — One or more mandatory inputs are incomplete or invalid.

Step 5 — Proposal Qualification produces `Structural Refusal`.

Step 6 — The structurally refused Proposal does not proceed to the Governance Decision Function.

## Ledger Delta

```text
ProposalReceived
ProposalQualificationStarted
StructuralValidationFailed
StructuralRefusal
Reason=SchemaValidationFailure
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
STRUCTURAL_REFUSAL
```

## Expected Result

```http
400 Bad Request
```

## Pass Criteria

The implementation passes this test only if:

- incomplete inputs result in Structural Refusal;
- Proposal Qualification verifies all required structural prerequisites;
- the structurally refused Proposal does not proceed to governance evaluation;
- malformed, incomplete, or structurally invalid Proposals are rejected before governance evaluation;
- Governance Evidence records the refusal reason.

## Fail Criteria

The implementation fails this test if:

- malformed Proposals proceed to the Governance Decision Function;
- the failure is treated as an ordinary policy denial;
- incomplete inputs are accepted;
- authorization is produced; or
- the refusal is not evidenced.

# TC005 — Provenance Validation Failure

**Requirement**  
CR-005 — Governance decisions SHALL require verifiable provenance where mandated.

**Normative Statements Covered**

- NS-6.4-02
- NS-7.4-01
- NS-10.4-01

**Conformance Level**  
L1 — Schema & Envelope Validation

## Test Objective

Verify that required provenance is validated before or during governance processing and that Governance Evidence records the provenance basis for the resulting outcome.

## Preconditions

- Provenance is required by policy or implementation profile.
- Proposal contains invalid, unverifiable, or incomplete provenance information.
- Other required structural fields are present.

## Request / Scenario

Submit a Proposal with invalid provenance information.

## Simulated Execution Trace

Step 1 — Proposal is submitted.

Step 2 — Proposal Qualification validates provenance qualification.

Step 3 — Provenance verification fails.

Step 4 — Proposal Qualification produces `Structural Refusal`.

Step 5 — Governance evaluation does not proceed.

Step 6 — Governance Evidence records the Proposal identity, provenance reference, processing outcome, and refusal reason.

## Ledger Delta

```text
ProposalCreated
ProposalQualificationStarted
ProvenanceQualificationFailed
StructuralRefusal
Reason=InvalidProvenance
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
STRUCTURAL_REFUSAL
```

## Expected Result

```http
400 Bad Request
```

## Pass Criteria

The implementation passes this test only if:

- provenance qualification is performed during Proposal Qualification;
- invalid required provenance prevents governance evaluation;
- Governance Decision Function processing is not used to authorize a Proposal with invalid provenance;
- Governance Evidence contains sufficient information to establish Proposal identity, provenance reference, processing outcome, and refusal reason.

## Fail Criteria

The implementation fails this test if:

- invalid provenance is ignored;
- governance evaluation proceeds despite failed mandatory provenance qualification;
- authorization is issued; or
- Governance Evidence omits the provenance failure.

# TC006 — Tenant Inactive on Submit

**Requirement**  
CR-006 — Governance evaluation SHALL enforce tenant operational status constraints.

**Normative Statements Covered**

- NS-11.1-01
- NS-11.4-01
- NS-8.4-01

**Conformance Level**  
L2 — Ordered Governance Mediation

## Test Objective

Verify that governance evaluation and authorization are constrained by the originating tenant and governance domain, and that inactive tenant status prevents authorization or commit eligibility.

## Preconditions

- Tenant status is `INACTIVE`.
- Proposal is submitted under the inactive tenant.
- Tenant and governance domain context are resolvable.

## Request / Scenario

Submit a Proposal under an inactive tenant.

## Simulated Execution Trace

Step 1 — Proposal is submitted.

Step 2 — Tenant identity and governance domain are established.

Step 3 — Tenant operational status is retrieved.

Step 4 — Tenant is determined inactive.

Step 5 — Governance processing refuses or denies the Proposal.

Step 6 — Execution Authorization, if invoked, verifies tenant and governance domain constraints and fails authorization.

## Ledger Delta

```text
ProposalCreated
TenantContextResolved
TenantStatusChecked
TenantInactiveDetected
GovernanceDecisionProduced
Decision=StructuralRefusal
ExecutionAuthorizationNotGranted
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
REFUSED
```

or

```text
DENIED
```

## Expected Result

```http
403 Forbidden
```

## Pass Criteria

The implementation passes this test only if:

- the governance decision is evaluated within the originating tenant and governance domain;
- tenant configuration and tenant status are not substituted from another tenant;
- inactive tenant status prevents authorization;
- Execution Authorization verifies tenant and governance domain constraints;
- Governance Evidence records tenant context and refusal or denial reason.

## Fail Criteria

The implementation fails this test if:

- an inactive tenant can submit an authorized Proposal;
- another tenant's status or policy is substituted;
- Execution Authorization ignores tenant constraints;
- execution becomes possible; or
- the tenant status decision is not evidenced.

# TC007 — Policy Not Found

**Requirement**  
CR-007 — Authorization SHALL require an applicable governance policy.

**Normative Statements Covered**

- NS-7.4-01
- NS-7.7-02
- NS-8.4-01

**Conformance Level**  
L2 — Ordered Governance Mediation

## Test Objective

Verify that governance evaluation resolves the complete applicable governance policy before authorization and that authorization fails when required policy cannot be resolved.

## Preconditions

- No applicable governance policy exists for the submitted Proposal.
- Canonical State is available.
- Proposal is otherwise structurally valid.

## Request / Scenario

Submit a Proposal for which no applicable governance policy can be resolved.

## Simulated Execution Trace

Step 1 — Proposal is submitted.

Step 2 — Proposal Qualification succeeds.

Step 3 — Governance Decision Function begins.

Step 4 — Applicable governance policy resolution is attempted.

Step 5 — No applicable governance policy is found.

Step 6 — Governance Decision Function produces a non-authorizing outcome.

Step 7 — Execution Authorization is not granted.

## Ledger Delta

```text
ProposalCreated
ProposalQualified
PolicyResolutionAttempted
PolicyNotFound
GovernanceDecisionProduced
Decision=StructuralRefusal
ExecutionAuthorizationNotGranted
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
REFUSED
```

or

```text
DENIED
```

## Expected Result

```http
404 Not Found
```

or

```http
403 Forbidden
```

depending on implementation profile.

## Pass Criteria

The implementation passes this test only if:

- Governance Decision Function attempts to resolve the complete applicable governance policy;
- evaluation does not produce authorization without applicable policy;
- the implementation demonstrates that it resolves all applicable governance policy before authorization;
- Execution Authorization verifies that governance configuration and prerequisites remain valid;
- Governance Evidence records the missing-policy condition.

## Fail Criteria

The implementation fails this test if:

- authorization is issued without applicable policy;
- a default-allow decision is produced;
- policy resolution failure is ignored;
- Execution Authorization authorizes execution; or
- the governance outcome does not identify the missing policy basis.

# TC008 — Idempotent Replay of Identical Proposal

**Requirement**  
CR-008 — Equivalent requests SHALL produce deterministic governance outcomes.

**Normative Statements Covered**

- NS-5.2.1-01
- NS-6.2-02
- NS-7.2-03

**Conformance Level**  
L3 — Deterministic Governance

## Test Objective

Verify that identical Proposals evaluated under identical governance conditions produce identical qualification and governance outcomes.

## Preconditions

- A Proposal has previously been submitted and evaluated.
- Governance configuration, applicable policy, Canonical State, and Governance Context remain unchanged.
- The same Proposal is resubmitted with identical canonical content.

## Request / Scenario

Submit an identical Proposal again.

## Simulated Execution Trace

Step 1 — Original Proposal is submitted.

Step 2 — Original Proposal Qualification completes.

Step 3 — Original Governance Decision Function evaluation completes.

Step 4 — Identical Proposal is submitted.

Step 5 — Proposal identity and canonical representation are compared.

Step 6 — Identical governance conditions are confirmed.

Step 7 — The same qualification and governance outcomes are returned or reproduced.

## Ledger Delta

```text
ProposalCreated
GovernanceEvaluationCompleted
ReplayDetected
DeterministicOutcomeReturned
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
Same outcome as original Proposal.
```

## Expected Result

Deterministically identical result.

## Pass Criteria

The implementation passes this test only if:

- identical Proposals under identical governance conditions produce identical Proposal Qualification outcomes;
- governance evaluation remains deterministic;
- the Governance Decision Function produces the same governance outcome;
- the implementation preserves deterministic governance behavior across replay;
- Governance Evidence records replay detection or deterministic reconstruction.

## Fail Criteria

The implementation fails this test if:

- identical inputs produce divergent qualification outcomes;
- identical inputs produce divergent governance decisions;
- replay changes lifecycle state improperly;
- replay produces non-deterministic evidence; or
- deterministic replay cannot be evidenced.

# TC009 — Governance Identity Conflict

**Requirement**  
CR-009 — Non-equivalent requests SHALL NOT share governance identity.

**Normative Statements Covered**

- NS-6.4-02
- NS-10.4-01
- NS-10.5-01

**Conformance Level**  
L3 — Deterministic Governance

## Test Objective

Verify that governance identity remains bound to the specific Proposal content and that non-equivalent payloads cannot reuse the same governance identity.

## Preconditions

- Existing Proposal identity is present.
- Existing Proposal content has been recorded.
- A modified non-equivalent Proposal attempts to reuse the same identity.

## Request / Scenario

Submit a modified Proposal using an existing request identity.

## Simulated Execution Trace

Step 1 — Modified Proposal is submitted.

Step 2 — Proposal Qualification validates proposal structure and identity attributes.

Step 3 — Existing governance identity is retrieved.

Step 4 — Submitted Proposal content is compared to the recorded Proposal content.

Step 5 — Non-equivalence is detected.

Step 6 — Proposal is refused or rejected as an identity conflict.

Step 7 — Governance Evidence records Proposal identity, processing outcome, and integrity basis.

## Ledger Delta

```text
ProposalReceived
GovernanceIdentityLookup
ProposalContentMismatch
IdentityConflict
StructuralRefusal
Reason=GovernanceIdentityConflict
GovernanceEvidenceGenerated
```

## Derived State After Request

```text
STRUCTURAL_REFUSAL
```

## Expected Result

```http
409 Conflict
```

## Pass Criteria

The implementation passes this test only if:

- Proposal Qualification verifies identity and proposal completeness;
- a non-equivalent Proposal cannot reuse an existing governance identity;
- Governance Evidence records Proposal identity, processing outcome, and relevant integrity/traceability information;
- evidence integrity and traceability are preserved.

## Fail Criteria

The implementation fails this test if:

- a non-equivalent Proposal is accepted under an existing governance identity;
- the recorded governance identity is overwritten;
- the original Governance Evidence is modified;
- authorization is produced; or
- the conflict is not attributable or traceable.

# TC010 — Retrieve Authorized Governance Object

**Requirement**  
CR-010 — Authorized governance state SHALL be externally retrievable.

**Normative Statements Covered**

- NS-10.4-01
- NS-10.6-01
- NS-10.7-01

**Conformance Level**  
L1 — Schema & Envelope Validation

## Test Objective

Verify that authorized governance outcomes are available as Governance Evidence and contain sufficient information to support retrieval, audit, conformance assessment, and deterministic reconstruction.

## Preconditions

- Authorized governance object exists.
- Governance Evidence was generated during governance processing.
- Caller is authorized to retrieve the object.

## Request / Scenario

Retrieve an authorized governance object or its associated Governance Evidence.

## Simulated Execution Trace

Step 1 — Retrieval request is received.

Step 2 — Governance object lookup is performed.

Step 3 — Associated Governance Evidence is retrieved.

Step 4 — Evidence content is inspected for required fields.

Step 5 — Evidence availability is verified.

Step 6 — Replay-supporting evidence is confirmed.

## Ledger Delta

```text
GovernanceObjectRead
GovernanceEvidenceRetrieved
EvidenceAvailabilityVerified
ReplaySupportVerified
```

## Derived State After Request

```text
AUTHORIZED
```

## Expected Result

```http
200 OK
```

## Pass Criteria

The implementation passes this test only if:

- Governance Evidence contains sufficient information to establish the governance decision, execution authorization if applicable, Canonical State reference, policy reference, Authority Lineage reference, tenant/domain context, timestamps, and processing outcomes where applicable;
- Governance Evidence remains available for audit, conformance assessment, HVA, Assurance Assessment, deterministic replay, and forensic investigation;
- Governance Evidence supports deterministic reconstruction of governance processing;
- retrieval does not expose unauthorized cross-tenant or cross-domain data.

## Fail Criteria

The implementation fails this test if:

- authorized governance state cannot be retrieved by an authorized requester;
- required Governance Evidence is missing;
- evidence is insufficient for deterministic reconstruction;
- retrieval returns incomplete or unauthenticated evidence;
- retrieval violates tenant or domain isolation; or
- replay support cannot be demonstrated.
